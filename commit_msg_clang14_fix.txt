fix(tests): clang-14 CI column — doctest's CAPTURE lambda cannot capture structured bindings, iterate pairs by member

The push of 317de4f went red on exactly one job: build-and-test
(linux-clang) failed at the Build step, while subject-lint,
linux-gcc-debug (ASan) and linux-gcc-release (tests + Python + UI)
were all green — the docs commit under it also green. That split was
the diagnosis: first-party code that compiles on gcc 11 and rejects
only on clang 14.

Root cause, reproduced exactly before touching anything: doctest's
INFO/CAPTURE expand to a deferred-context LAMBDA —

    DOCTEST_INFO_IMPL: MakeContextScope([&](std::ostream* s) { ... })

— and a structured binding is not lambda-capturable on clang <= 15
(P1091 capture of bindings landed in clang 16). gcc 11 accepts the
construct, which is precisely why every gcc column was green while
the clang column failed to build. The four hits were the four
CAPTURE(name) loops over pair arrays in test_g1_data_model.cpp —
the only structured bindings in the G1 unit-1 code.

Reproduction (no sudo, the CI pairing bit for bit): clang
14.0.0-1ubuntu1.1 from the jammy archive extracted user-land, driven
against libstdc++-11 headers via --gcc-toolchain (ubuntu-22.04 = g++
11.4 headers, the toolchain contract of the warning audit). Before
the fix it produced the CI's four errors verbatim ("reference to
local binding 'name' declared in enclosing function"); a plain
by-reference capture probe confirms the split empirically — clang 14
rejects even [&]{ return a; } on a binding, gcc and clang 18 accept.

The fix: the four loops iterate the pair by member (entry.first /
entry.second) so no structured binding ever reaches the macro's
lambda, with the why pinned as a comment at the first site so the
pattern does not quietly regress. No behavior change: same fixtures,
same assertions, same coverage. One cosmetic delta, declared: the
CAPTURE label in a failure report now reads "entry.first" instead of
"name".

Verification on the fixed tree: linux-clang reproduced locally —
build green, 580/580 cases, 267,134/267,134 assertions; gcc release
(-Werror) 580/580; gcc debug + ASan/UBSan 580/580, stderr clean;
Python 3.12 offscreen 124 passed + 4 documented GL skips, exit 0
(the nanobind leak warning is the known pre-existing one); GL smoke
under Xvfb + EGL 13/13, zero skips; f-string checker 42 files clean;
goldens untouched (git status: only this file).

Discovered, pre-existing, deliberately NOT fixed here (out of the
commit's scope, reported for a maintainer decision):
tests/unit/bridge/test_bridge.cpp:1459 — 'rejections' is incremented
but never read, unlike its siblings composites/pure_columns which
are CHECKed. Inert on the current CI matrix (gcc has no
-Wunused-but-set-variable for C++; clang 14 predates its C++
enablement) but fires under -Werror on clang >= 17 — a one-word
cleanup or a missing CHECK to land, whichever was intended.

Process note: the gap that let this through is that the clang column
was never reproducible in this environment (no sudo, no clang). It
now is — user-land clang-14 + gcc-11 headers, exact CI pairing — so
future units can run the full local matrix (gcc release, gcc
ASan/UBSan, clang 14) BEFORE the push, as the workflow's toolchain
contract prescribes.
